現有系統

遷移的起點：一個真的會查資料庫的 COBOL 系統

不是教材裡的玩具範例——是一條瀏覽器點下去、COBOL 執行檔真的去 shell 出 sqlite3 查資料的完整路徑。

資料流是這樣走的：前端送出請求，Node.js 的 Express API 收到後直接 spawn 一支編譯好的 COBOL 執行檔，把參數用一行 JSON 字串從 stdin 餵進去； COBOL 程式跑完，把結果印成 JSON 字串到 stdout，Node.js 讀回來、轉發給前端。COBOL 程式本身沒有連任何資料庫 driver——它是用 CALL 'SYSTEM' 呼叫 sqlite3 這支命令列工具，把查詢結果讀進暫存變數再組回 JSON。

這個資料存取方式（shell out 呼叫 CLI）是為了讓練習複雜度可控而簡化過的寫法， 不是真實世界 COBOL 系統常見的樣貌（真實系統多半是 embedded SQL、CICS、 VSAM）。這對「練習 AI 工具怎麼做遷移」是優點：邏輯好讀、好驗證，但也代表這次練習 會遇到的複雜度，跟真正的大型主機遷移案還是有落差。

容易被 AI 順手「優化掉」的細節：COBOL 手刻的 STRING/UNSTRING JSON parser、定長欄位的 trailing space、PIC 9(10)V99 的隱含小數精度、 PIC Z,ZZZ,ZZ9.99 這類數值格式化——翻譯成 Java 時如果沒有逐行對照原始碼， 很容易看起來邏輯差不多、實際上輸出對不上。
四階段方法論

理解 → 規劃 → 建護欄 → 遷移

每個階段的產出都是下一階段的輸入，串起來才是完整的遷移練習——不是「看起來邏輯差不多」就收工。

01

用 Bob 理解 codebase

請 Bob 逐支說明每支程式的職責、輸入輸出 JSON schema、業務規則的魔術數字（門檻值、時間窗口）， 並要求「每個結論都要能對應到 PROCEDURE DIVISION 裡實際的程式碼行」，不能憑經驗腦補。

→ docs/cobol-understanding-report.md
02

切到 Plan mode，規劃遷移

基於理解報告，規劃目標架構（單純 Java class 還是 Spring Boot service）、COBOL → Java 對應表、遷移順序（風險最低的先做，ALERTMGR 最後）、測試涵蓋範圍，以及數值精度／日期格式／ 字串定長等風險清單。這階段只出計畫，不動程式碼。

→ docs/migration-plan.md
03

測試先行，先幫 COBOL 建護欄（characterization tests）

用 database/mock-data.sql 固定測資，把各種輸入 JSON 丟給編譯好的 COBOL 執行檔，將 stdout 的輸出存成 fixture 當作 golden output。這一步只釘住現有行為， 就算判斷式看起來怪怪的也照實記錄，不自己「修正」。

→ tests/fixtures/<程式>/<案例>.expected.json
04

逐支遷移，跑測試比對

依照 migration-plan.md 的順序，一支一支走「重讀 COBOL 原始碼 → 寫 Java → 跑 characterization test 比對 fixture → 全過才進下一支」的循環。輸出不一致時， 先判斷是翻譯錯了還是 fixture 記錄了 COBOL 本身的 bug，兩種情況都要跟講師/隊友確認， 不要自己決定要不要保留 COBOL 的行為。

→ 10 支全數遷移完成、測試全過
驗收標準：同一組 mock data、同一組輸入 JSON，COBOL 版本與 Java 版本 輸出完全一致（數值精度、日期格式、字串內容都要對上），而不是「看起來邏輯一樣」。

Windows 學員：請用 WSL2 + Ubuntu 執行 COBOL 版本，全程在 WSL 終端機裡操作。 COBOL 內部用 CALL 'SYSTEM' 執行的是 Unix shell 語法。 若想簡化流程，也可以跳過執行COBOL，直接從COBOL -> Java 轉換開始。
